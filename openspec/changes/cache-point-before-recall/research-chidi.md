## Bedrock (docs + source; no AWS credentials present, no probe run)
- pi marks points in `api/bedrock-converse-stream.js`: system block gets one `cachePoint` (`:739-746`, `buildSystemPrompt`), and the last user message gets one (`:932-942`). No tool `cachePoint` is added (grep shows only those two sites). **2 points total** when `supportsPromptCaching` (`:703-726`: Claude 5.x, any `-4-`, 3.7 Sonnet, 3.5 Haiku; non-Claude only with `AWS_BEDROCK_FORCE_CACHE=1`).
- Limit: [B] "up to 4 for Claude models" (4 for every listed Claude row); so adding one point before recall's block (3 total) is within limit, with a free slot for a tools point.
- Help vs harm: the same failure applies. The last-user-message `cachePoint` is appended after the last content block (recall's), and [B] says "The check finds only entries that earlier requests wrote, so a single checkpoint at the end of content that stays the same across requests, before any content that changes, is often enough." A point in `messages` before recall's block should help; a point *replacing* the last-message one is the equivalent of the OAuth "move".
- Minimums [B]: 4,096 for Haiku 4.5 / Opus 4.5-4.7; 1,024 for Sonnet 4.6/5, Opus 4.8; 512 for 5.x Opus/Fable/Sonnet 5.5/Haiku 5.5. "If you add a cache checkpoint before the total prefix meets the minimum... your inference still succeeds, but your prefix isn't cached." Minimum applies to the cumulative prefix across tools+system+messages.
- Extra constraint [B]: a 1-hour-TTL entry must precede 5-minute entries ("Cache entries with longer TTL must appear before shorter TTLs"); pi sets `ttl` only when `cacheRetention === "long"`, so an added point must carry the same TTL as pi's (inherit it).
- Bedrock Converse payload shape differs: a point is a separate `{cachePoint:{type:"default"}}` content item, not a field on a block. An extension targeting `cache_control` will not touch it. **Unverified by probe.**
- Also worth noting: [A] "Automatic caching is available on every platform except Amazon Bedrock (bedrock-runtime)" (400 on top-level `cache_control` there); [B] says Converse accepts it via `additionalModelRequestFields` for listed models. Not relevant to pi's current path.

## Other providers pi supports with explicit points (missed by the list)
- Every provider routed via the `anthropic-messages` api shares the Anthropic marking: `anthropic`, `minimax`, `minimax-cn`, `opencode`, `opencode-go`, `cloudflare-ai-gateway`, `vercel-ai-gateway`, `fireworks`, `github-copilot`, `openrouter` (`providers/*.js` `anthropicMessagesApi()` registrations). Fireworks data sets `supportsCacheControlOnTools` (`providers/data/fireworks.json`) so its point count may be 2 not 3; value not read. I did not probe any of these; the OpenRouter result does not prove the others.
- `cacheControlFormat:"anthropic"` is a user-settable compat field for **any** openai-completions model (`providers/compat-schema.js:203`), so custom/gateway models in a user's models.json can carry points. Auto-detected only for OpenRouter `anthropic/*`.
- OpenAI `prompt_cache_key` and `prompt_cache_retention` (`openai-completions.js:566-573`): not explicit points.
- Bedrock non-Claude (Nova): points only with `AWS_BEDROCK_FORCE_CACHE=1`; [B] says Nova supports `system` and `messages` checkpoints, 4 max.

## Can Anthropic show which entry a request resumed from?
Yes, beyond `cache_read_input_tokens`: **cache diagnostics** [D] (Claude API only; supported models include Haiku 4.5 and the 4.x-5.x lines). Request carries `diagnostics:{previous_message_id: <prior response id>}` (first turn `null`); response (or `message_start` when streaming) carries `diagnostics.cache_miss_reason.type` of `model_changed | system_changed | tools_changed | messages_changed | previous_message_not_found | unavailable`, plus `cache_missed_input_tokens` on the `*_changed` types (a byte-length estimate). It reports where the request *structure* diverged from the previous one, "independent of whether the cache actually hit" — it does not name the entry resumed from. Limits [D]: Claude API only (no Bedrock/Vertex/OpenRouter), same workspace, short retention, "best-effort", can report `unavailable` for deep divergences or changed `thinking`/`tool_choice`/beta headers. Documented examples use `client.beta.messages` (SDK beta namespace); I did not verify whether a beta header is required. A pure append (the case when the point sits before recall's block) would show `null`. Other fields: `usage.cache_creation` split into `ephemeral_5m_input_tokens` / `ephemeral_1h_input_tokens` [A]. `total_input = cache_read + cache_creation + input_tokens` [A].

## Differences from the brief's assumptions
1. Item 2: a 5th point errors (400), not silent.
2. Item 4: `system`/`tools` markers *are* in the thread hash; only message markers are stripped.
3. Item 5: OpenRouter Anthropic models took the anthropic-messages path in the probes (3 points incl. system), not the "tool + last user part" description; probe logger omitted `system`.
4. Item 6's "reads 0–10k" baseline matches OAuth `system[0]`+`system[1]` points producing a 10,364-token system-prefix read.

## Gaps
- Bedrock: no credentials, no probe; behaviour of an extra `cachePoint` content item unmeasured.
- Providers other than Anthropic OAuth/API key/OpenRouter (Vercel, Cloudflare, OpenCode, MiniMax, Fireworks, Copilot) unprobed.
- Thread continuation never observed in probe logs (`thread.type:"create"` every turn), so "moving a point can't break continuation" rests on source reading.
- Gemini implicit-cache pricing from probe logs only.
- Model-specific minimum for Opus 5.5 etc. from docs only; probes used Haiku 4.5 (4,096).
- Whether cache diagnostics needs a beta header is unverified.
- I did not re-run the OAuth or API-key 3-turn probes; I ran two OpenRouter Haiku 4.5 requests (a few cents) and removed my scratch files.
