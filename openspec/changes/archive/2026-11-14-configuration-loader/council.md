# Council Synthesis

## Question and Scope

**The design question.** How does taiknr resolve a per-session configuration from two optional JSON files — `<agent dir>/pi-taiknr.json` and `<cwd>/<CONFIG_DIR_NAME>/pi-taiknr.json` — and hand it to seven handlers registered at factory time, when the factory has no working directory and no trust state, a rejected file must leave the session fully inert (Joel's Q1(b)), and the configuration must reach the handlers without breaking the seven-registration invariant or the frozen registrar signatures (D6)?

The change is `proposal.md`. The behaviour is `specs/configuration/spec.md` and the MODIFIED `specs/extension-packaging/spec.md`. This synthesis settles the questions those two artifacts left to the council; it does not restate them.

## Lens Findings & Trade-offs

### council-zoom-out — simpler or more speculative?

Recommended the loader in `src/config/`, path resolution at the composition root, lifecycle orchestration in the existing session-start handler, `node:fs` plus hand-written guards, and one replaceable per-extension holder. Findings: **ZO-1 (major)** the preserved two-path `ConfigPaths` gives the caller no way to exclude an untrusted project file; **ZO-2 (major)** neither a `TaiknrConfig` nor an `enabled`-only holder distinguishes "rejected" from "turned off", and a handler throw does not make the other six handlers inert; **ZO-3 (minor)** the spec puts trust and `session_start` wiring tests under `tests/config/` when they exercise `src/app/` and `src/infra/`. Owner question: O7, recommended silent.

### council-critic — what breaks?

Recommended design go ahead with "six major contract fixes and no blocking findings", and judged cost a non-issue: two small synchronous reads per session start, and `enabled: false` removes classifier spend. Findings: **CR-1 (major)** a holder carrying only a resolved config lets a later `/taiknr on` resurrect the defaults Q1(b) forbids — three states needed; **CR-2 (major)** `ConfigPaths.projectConfigPath` is a required string, so trust cannot reach the loader, and an untrusted repository can brick taiknr; **CR-3 (major)** the MODIFIED `extension-packaging` block contradicts itself, because turn-end and context are among the six registrars and their `config` member is the config-carrying one; **CR-4 (major)** rejecting a BOM-prefixed object is stricter than Pi, which strips the BOM before every JSON config read it does; **CR-5 (major)** "missing" is undefined in terms of read errors, so a dangling symlink that is likely under Joel's dotfiles setup falls back to defaults silently; **CR-6 (major)** the seam must state its lifetime and what re-enabling does to the store, not just be a boolean; **CR-7 (minor)** O3 is settleable from source, and the design still owes an order of operations and a message scope; **CR-8 (minor)** typebox does not pay for itself, and hand-written guards have two edge cases to pin; **CR-9 (minor)** Pi gives extensions no logging channel, so the design must say the success path logs nothing; **CR-10 (minor)** the two behavioural "off" scenarios cannot be tested in this change and nothing says which card verifies them.

### council-comprehension — can a user and an implementer follow it?

Recommended an explicit per-session state holder, one future handler-guard convention, and actionable diagnostics and recovery before implementation. Findings: **CC-1 (major)** the error state and recovery path are not distinguished from `enabled: false`, and a future command must not bypass a rejection; **CC-2 (major)** the report's delivery in JSON mode is asserted by the orientation and not established by the research; **CC-3 (major)** "names the file and the field" is unsatisfiable for parse failures and non-object roots; **CC-4 (major)** the outcome of an existing but unreadable file is unspecified; **CC-5 (major)** the guard convention must exempt the config path and must read current state, not a startup snapshot; **CC-6 (minor)** the caller-to-loader representation of an untrusted project layer is undefined; **CC-7 (minor)** nothing lets a user discover a deliberate off. Owner questions: O7, recommended one mode-appropriate notice; and whether an unreadable file is a session-stopping failure or treated as absent, recommended a reported failure.

### council-structural — does each fact have one home?

Recommended design proceed after settling three structural gaps. Findings: **STR-1 (major)** the trust gate's mechanics and ordering are unspecified, and cannot be inferred from a signature that takes both paths; **STR-2 (major)** in-place fill of a shared `TaiknrConfig` has an undefined stale-state transition when a `session_start` throws before the fill, so session B can run on session A's values with nothing reported; **STR-3 (major)** two distinct causes of inertness — a rejected file and `enabled: false` — have no single named predicate, so three later cards risk inventing three ways; **STR-4 (minor)** "exactly the ones the design names" is circular until `design.md` exists, so the gate cannot compare against HEAD mechanically; **STR-5 (minor)** the `configuration` spec restates test conventions the living `development-checks` spec already owns; **STR-6 (minor)** the seven-registration invariant funnels resolution, trust, reading, reporting, ordering against hydration and the holder write into one session-start handler that is becoming a god handler. Owner question: whether an untrusted project file that is malformed is ignored unread or still rejects the session, recommended ignored.

### council-readiness — can a coder implement this without deciding anything?

Recommended a design that leaves Derek no choices. Findings: **R1 (major)** the loader cannot be told to skip the project file under the unchanged `ConfigPaths`; **R2 (major)** the holder's type, state set and method names are unnamed, and a rejected file has no representation in a plain `TaiknrConfig`; **R3 (major)** the error shape is undecided — class, fields, first or all violations, and what "field" means for parse and I/O failures; **R4 (major)** O6 gives three later cards three ways to check `enabled`, and a guard over no-op handlers has no behavioural test today; **R5 (major)** `CONFIG_DIR_NAME` is an import-time constant, so the non-`.pi` scenario cannot be driven from a test without injection or a host mock; **R6 (major)** strict unknown-key rejection makes every future field a version-skew break for a committed, shared project file; **R7 (major)** the spec's test locations contradict the mirror rule, and the existing fake cannot supply a `ctx`; **R8 (minor)** validation boundary cases are incomplete (`1e999`, `-0`, whitespace-only model strings, `__proto__`); **R9 (minor)** the observability bar has no channel, and a `console.log` would corrupt JSON stdout; **R10 (minor)** the order inside the session-start handler is not fixed; **R11 (minor)** a session that starts off skips hydration, so `setEnabled` alone is not enough for the Status card; **R12 (minor)** O2 is cheap to close as hand-written guards. Owner question: O7, recommended silent.

### council-codebase — does this match the tree as it is?

Paraphrased both the proposal and the current state, and confirmed every cited path, symbol, signature and line matches the live tree. Findings: **CB-1 (major)** `config: TaiknrConfig` is plain data and cannot express Q1(b), and the delta's "carry the session's configuration" under-authorizes the shape the design needs; **CB-2 (major)** no artifact fixes the rejection message's format or channel, which is the user's only signal; **CB-3 (minor)** "every rejection names the file and the field" is unsatisfiable for malformed JSON; **CB-4 (minor)** a present-but-untrusted project file is indistinguishable from an absent one in every output, the hardest case to triage; **CB-5 (minor)** the proposal wires the session config to "the scorer adapter", but `createPiJevScorerAdapter` has no call site at HEAD, so the clause is unassertable; **CB-6 (minor)** the repository contains no logging of any kind, so O5 starts from nothing. Owner question: O7, recommended log-only (no user-facing notice).

### council-catalyst — where is the leverage?

Recommended three minimal transforms together: a segmented session-config holder with an initial inactive state and `setEnabled(boolean)` as the command seam; a fail-closed reset before `loadTaiknrConfig` runs in `session_start`; and a six-line gated `pi` Proxy for the six non-session-start registrars so no handler signature changes. Findings: **CAT-1 (major)** O1, O3 and O6 accept a false compromise between preserving the registrar signatures and enforcing session-wide inertness, because four of the six registrars have no config parameter and a throw skips the rest of `session_start` without stopping the other six events; **CAT-2 (major)** a required `projectConfigPath` leaves only bad options — parse an untrusted file, or pass a sentinel path non-Pi callers must guess; **CAT-3 (minor)** O5 as push logging conflicts with silent missing-file startup, JSON stdout purity and D10's exclusion of UI readouts, so the resolution should be pull state and a throw. Owner question: O7, recommended silent.

## Synthesis & Recommendation

The council converged on one direction, and Michael's rulings fix it. The design implements this, and nothing else:

1. **A three-state holder, one per factory call** (`unresolved` | `rejected` carrying the `TaiknrConfigError` | `ready` carrying the config), with three operations: one whole-state assignment per `session_start`, `isActive()`, and `setEnabled(boolean): boolean` that refuses unless ready. Initial state inert; never module-level (ruling 1).
2. **`ConfigPaths.projectConfigPath: string | undefined`**, so the trust decision is stated by the caller; the session-start handler sets it only when `ctx.isProjectTrusted()`, and the loader never opens, parses or validates a file it was not given (rulings 2, 3).
3. **One gate at the composition root**: a small named function in `src/app/extension/` wrapping `pi.on` so a registered handler runs only while `isActive()`; the six non-session-start registrars get the gated `pi`, `registerSessionStartHandler` gets the raw `pi`; handlers read the holder at event time; later cards add no per-handler check (ruling 4).
4. **One `Error` thrown from the session-start handler** after the holder is set to `rejected`, and nothing else; measured visible in print, JSON, RPC and TUI; message `<absolute file path>: <field>: <reason>` (or without the field when none applies) ending with the recovery line (ruling 5).
5. **Hand-written validation** in `src/config/taiknr-config.ts` as one per-field rule table next to the defaults, with one `TaiknrConfigError` class, first violation reported, `field` undefined for parse, root and read failures, and the measured edge cases as test rows; `package.json` untouched (ruling 12).
6. **Read errors classified**: only a path with no directory entry is absent; a dangling symlink, `EISDIR`, `EACCES` and every other read error are rejections naming the file (ruling 8). A leading BOM is stripped before parsing (ruling 7).
7. **Tests mirror the layer they exercise**: `tests/config/` for the host-free loader, `tests/app/extension/` for the holder and the gate, `tests/infra/pi-event-handlers/` for the session-start handler, the existing entry test unchanged, one shared handler-capturing fake under `tests/` (ruling 9).
8. **No `ConfigResolution` record and no output on success or absence**; the rejection throw is the only emission; two hand-offs recorded (ruling 14).
9. **Nothing extra in the session-start handler**: two `join`s, one `loadTaiknrConfig` call in try/catch, one holder assignment, one rethrow, then the hydration slot a later card fills (ruling 18).
10. **`enabled: false` is silent** (Joel's O7 → (a)).

Rejected on the evidence: in-place fill of the shared `TaiknrConfig` (it cannot carry `rejected`, and it needs an initial value that is the defaults Q1(b) forbids); a per-handler inertness predicate (four of the six registrars have no config parameter, so it forces a signature change in each later card); typebox (a peer entry, a message formatter still needed, and a host-mapped import inside the host-free layer); a separate resolution orchestrator (one caller, and every non-trivial responsibility already has a home); a stored resolution record (no consumer in this change); and a version string or deprecation window in the message (the manifest has no `version`, and removal belongs to the card that removes a field).

## Michael's Rulings

Eighteen items were put to Michael. Seventeen are `settled` and bind `council.md`, the specs and `design.md`. The eighteenth (O7) is Joel's and he ruled (a); it is recorded under Owner Decisions Required.

**1. O1 — the holder's shape, states and lifetime. Settled.** Three states (`unresolved` from factory time until the first `session_start`, `rejected` carrying the `TaiknrConfigError`, `ready` carrying the resolved `TaiknrConfig`), one holder created per factory call in `src/app/extension/`, `enabled` a field of the ready config rather than a fourth state. Three operations: assign the whole state once per `session_start` (whole replacement, so a fixed file clears a prior rejection), `isActive()` = ready and `enabled`, `setEnabled(boolean): boolean` that returns false and changes nothing unless ready. In-place fill of the shared `TaiknrConfig` is rejected: it cannot carry `rejected` and needs an initial value that is the defaults Q1(b) forbids. The holder is never module-level. *Decided by:* Joel's Q1(b) plus measurement of Pi 1.5.2 `loader.js` L470–500 and L519: `loadExtensionModule` caches the factory, `initializeExtension` runs it on every load, so a factory-local holder is per session and module state leaks.

*Placement revised after this council, on consult.* The states, operations and per-factory lifetime above stand unchanged; the unit moved from `src/app/extension/` to `src/config/session-config.ts`. The infra handlers name the holder in their contracts, so declaring it in the composition root would make three infra handlers depend on `src/app/`, which `ARCHITECTURE.md` §3 keeps to the Pi extension alone; the house precedent is `RecallCache`, declared in `src/use-cases/` and imported as a type by `src/infra/pi-event-handlers/context.ts:4` (`research-eleanor.md` addendum, which also records that nothing written forbids an infra→app edge and that none exists at HEAD). The design carries the reasoning in its "Dependency direction" and "Why the two new units cannot live in an existing module" passages. 

**2. How trust reaches the loader. Settled.** `ConfigPaths` becomes `{ agentConfigPath: string; projectConfigPath: string | undefined }` — the key stays required so the caller must state the trust decision, and `undefined` means "no project layer". The session-start handler sets it only when `ctx.isProjectTrusted()`; the loader never opens, parses or validates a file it is not given. An ordered path list is rejected: the deferred env layer is not a file path. This is a narrow revision of D9, recorded as such. It needs no `extension-packaging` entry as a registrar contract (row 6 lists it for the reviewer's single list). The `configuration` spec gains the scenario "an untrusted project file that is malformed is never read and causes no rejection". *Decided by:* Pi `docs/extensions.md` L1197–1201, S4, and the deletion test; pi-jefferson gates at the caller the same way.

**3. Untrusted project file, malformed. Settled.** Ignored unread. Joel's Q1(b) was answered about files taiknr reads; an untrusted project file is one taiknr must not read, so "present but malformed" never arises. The security consequence decides it: otherwise any repository the user `cd`s into can switch taiknr off before trust is granted. No question for Joel. *Decided by:* `docs/extensions.md` L1197–1201 (trust check precedes the read), the project-trust model in `docs/security.md`, and Joel's Q1(b) wording scoped to files taiknr legitimately reads.

**4. O6 — where the inertness check lives. Settled.** One gate at the composition root as a small named function in `src/app/extension/` wrapping `pi.on`, so a handler runs only while `holder.isActive()`; the six non-session-start registrars receive the gated `pi`, `registerSessionStartHandler` receives the raw `pi`. Four of the six have no config parameter, so a per-handler predicate forces a signature change in each later card, against D6 and `AGENTS.md`. Measured: the gate type-checks with one typed cast over Pi's overloaded `on`, Biome is clean, the entry test stays green, and the wrapper returns `undefined` while inactive and the handler's result once active. The design records the cast as the one place the host's `on` typing is bypassed, and the rule that handlers read the holder at event time and never capture a `TaiknrConfig` at factory time. *Decided by:* D6 and measurement in a `git archive HEAD` copy.

**5. O3 and CC-2 — how a rejection surfaces in every mode. Settled.** One `Error` thrown from the session-start handler after the holder is set to `rejected`, and nothing else — no `ctx.ui.notify`. Measured live in Pi 1.5.2: `pi -p` prints `Extension error (<ext path>): <message>` on stderr; `pi --mode json` prints the same on stderr while stdout carries only the session record, so the JSON stream is untouched. Source confirms TUI and RPC. Handler order: build paths from `ctx` → `loadTaiknrConfig` in try/catch → assign the holder → rethrow on rejection → hydration slot (later card) only when `isActive()`. Message: `<absolute file path>: <field>: <reason>`, or without the field when none applies, ending with "fix the file, then run /reload or start a new session". No `pi-taiknr:` prefix is required, because the host already prefixes the extension path. *Decided by:* the live run plus `print-mode.js` L86, `rpc-mode.js` L267 and `agent-session.js` L2772–2776.

**6. The MODIFIED `extension-packaging` block. Settled.** Rewritten to enumerate the permitted differences by name: (1) `registerSessionStartHandler` gains the holder and keeps `_pi` and the store; (2) the `config` member of `registerTurnEndHandler`'s and `registerContextHandler`'s deps objects changes type from `TaiknrConfig` to the holder; (3) the `ConfigPaths.projectConfigPath` type, recorded under D9 and listed here so the reviewer has one list. Everything else is unchanged against HEAD, including the other four registrars' full signatures, turn-end's and context's other members, `createPiJevScorerAdapter(ctx, config: TaiknrConfig)` and the ports. The scenario compares the diff with that list. *Decided by:* one fact, one place, and the measurability requirement for a gated scenario, following the first change's mechanical comparison with HEAD.

**7. A UTF-8 BOM. Settled.** Strip a leading U+FEFF before `JSON.parse`; a BOM-prefixed `{}` is valid. `""` and `" "` stay rejections, and the test row flips to "accepted". Trap 7 recorded a Node fact, not a contract; the host's own convention is the closest community practice under D2. *Decided by:* thirteen `stripBom` read sites in Pi 1.5.2 `dist/` (`settings-manager.js` L269/L452, `extensions/mcp/config.js` L48/L180, `config.js` L466/L480, `resource-loader.js` L39, `pi-manifest.js` L9, `migrations.js` L30/45/144, `package-manager-cli.js` L37, `interactive-mode.js` L1095) and a Node 26.8.1 measurement that the stripped text parses.

**8. A present but unreadable file. Settled.** Broken, not absent. Only a path with no directory entry is absent: read in try/catch; on `ENOENT` run `lstatSync` — if that also fails `ENOENT` (or the read failed `ENOTDIR`, i.e. `<cwd>/<CONFIG_DIR_NAME>` is not a directory) the file is absent and silent; if `lstat` succeeds the entry is a dangling symlink and it is a rejection naming the file. `EISDIR`, `EACCES` and every other read error are rejections naming the file with no field and the errno in the reason. Joel's Q1(b) reason covers it: taiknr must never run on values the user did not choose, and `~/.pi/agent` is dotfile-managed, where a link target can go missing. Not a question for Joel. *Decided by:* Joel's Q1(b) and Node 26.8.1 errno measurements (missing file, dangling symlink, directory, and a path through a regular file).

**9. Test locations and conventions. Settled.** Tests mirror the `src/` layer they exercise: `tests/config/` for the host-free loader cases; `tests/app/extension/` for the holder and the gate; `tests/infra/pi-event-handlers/` for the session-start handler (paths from a fake `ctx`, trust gate, assign/throw order, re-read on a second call with a different cwd); the existing entry test unchanged. A handler-capturing fake of `ExtensionAPI` with a `ctx` stub is needed by more than one file, so it has one home under `tests/` at the path the design names; it is not collected (the include is `tests/**/*.test.ts`) and is still linted and type-checked (`tests/**`). The `configuration` requirement keeps only the config-specific coverage list and cites `development-checks` for conventions. *Decided by:* D7 and one-fact-one-place, with `vitest.config.ts`, `biome.json` and `tsconfig.json` scopes read at HEAD. *(The holder's test follows the holder into `tests/config/`, per the placement revision noted under ruling 1.)*

**10. `CONFIG_DIR_NAME` testability. Settled.** The scenario is reworded to what is observable: "the project path is built from the host's `CONFIG_DIR_NAME`, and `src/` contains no literal `.pi` or `~/.pi` path segment" (a source search), plus the agent-path scenario tested by pointing `PI_CODING_AGENT_DIR` at a `mkdtemp` directory (measured working under vitest). The file name is one exported constant in `src/config/taiknr-config.ts`. *Decided by:* the measurement that `CONFIG_DIR_NAME` is evaluated at module load (`config.js` L492), S1, and the deletion test.

**11. Unknown-key rejection and version skew. Settled.** Joel's Q1b stands: an unknown key is a rejection naming the file and the key, with the reason "unknown field". No version string in the message, because the manifest has no `version` and Pi's exported `VERSION` is Pi's. No deprecation window is designed now; it belongs to the card that removes a field, if one ever does. The design's Risks records the skew consequence and the rollback note; "field X requires version Y" is the publishing card's, when there is a version. *Decided by:* Joel's "Q1b, reject it", `package.json` at HEAD having no `version`, and the first change's Decision 9.

**12. O2 — typebox or hand-written validation. Settled.** Hand-written guards in `src/config/taiknr-config.ts`, as one per-field rule table next to the defaults. D2 does not decide it — Chidi's sample shows hand-written, zod and typebox all in use, and the one sibling that validates does it by hand — so the deletion test does: typebox adds a `peerDependencies` entry, still needs a message formatter, and puts a host-mapped import inside the layer that must be callable with no Pi runtime. Pinned rules, with the measured edge cases as test rows: known keys checked with `Object.hasOwn` or a `Set`, so `toString` is rejected as unknown and `__proto__` — an own key after `JSON.parse` — is rejected, never spread; `decisionThreshold` through `Number.isFinite` then `0 ≤ x ≤ 1`, so `1e999` is rejected and `-0` accepted; `minCharsToArchive` through `Number.isInteger` then `≥ 0`; the two model fields strings with `trim().length > 0`; `enabled` `typeof === "boolean"`. **13. O7 — announcing a valid `enabled: false`. Marked `joel`.** Michael's recommendation was (a) silent. Joel ruled (a) silent; see Owner Decisions Required. *Decided by:* none — product behaviour.

**14. O5 — observability. Settled.** This change emits nothing on success and nothing on absence, and the rejection throw is the only emission. No `ConfigResolution` record: its only consumers in this change would be its own tests, and the Status card that would read it does not exist yet. The rejected state carries the path, field and reason; the ready state carries the config. The design records two hand-offs: "present but untrusted project file, ignored" is indistinguishable from "absent" in this change, and the Status card decides what it exposes and adds the record then; and the orientation's O5 bar is met here by the rejection path alone, stated plainly, not by a log that has nowhere to go. *Decided by:* S2, the deletion test, and the measurement that Pi offers extensions no logging channel.

**15. The command seam's contract and lifetime. Settled.** The seam is the holder's `setEnabled(boolean): boolean`, not a bare field. It succeeds only in `ready`, so a fixed-but-unreloaded rejection stays closed until `/reload` or a new session, and the refusal is why the rejection message names the recovery step; its effect lasts until the next `session_start`, which re-reads the files; it does not hydrate, and turning on mid-session after hydration was skipped is the Status card's hazard when it wires the command. Nothing else is built here. *Decided by:* Joel's "The /taiknr on|off command" and Q1(b), the factory-per-load measurement, and the lifecycle table in `docs/extensions.md` L376–392.

**16. CB-5 — the scorer adapter. Settled.** Drop the adapter from this change's wiring requirement. The requirement names the two deps members (turn-end, context) that receive the holder; the recall card constructs the scorer adapter inside the context handler from the holder's ready config, and its signature stays `(ctx, config: TaiknrConfig)`. The spec's "every handler and adapter that needs a `TaiknrConfig`" becomes "the turn-end and context handler dependencies". *Decided by:* no caller of `createPiJevScorerAdapter` at HEAD, and the rule that a SHALL without an observable has no test.

**17. CR-10 — the behavioural "off" scenarios. Settled.** Keep the scenarios, because they state Joel's Q3 contract, and mark each in the spec as verified by the archive and recall cards through the composition-root gate. This change tests what exists: the holder's state for `enabled: false`, `rejected` and `unresolved` all make `isActive()` false; the gate does not invoke a registered handler while inactive and does once active; the trust-gated project `enabled: false` resolves correctly. No test is written against an invented handler body. *Decided by:* Trap 12 and the first change's precedent of recording deferral explicitly.

**18. STR-6 — the session-start handler as a god handler. Settled.** No separate orchestration function. After the rulings above the body is four steps: two `join`s from `ctx` and the host helpers, one `loadTaiknrConfig` call in try/catch, one holder assignment, one rethrow. Validation and layering live in `src/config/`, the state machine in the holder, the gate in the composition root; the handler is the thin bridge ARCHITECTURE §3 describes. The Status card's re-validation reuses `loadTaiknrConfig`. The design may extract one function if the handler grows past those steps when the archive card adds hydration. *Decided by:* the deletion test and the placement already fixed by rulings 1, 4, 10 and 12.
