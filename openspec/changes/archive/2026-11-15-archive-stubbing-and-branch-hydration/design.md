# Design

## Context

The seams already exist and every body is missing. `src/domain/` declares `ToolOutputCandidate` and `ArchivedToolOutput` and a `buildStub` that throws; `src/use-cases/` declares `ArchiveStore` and the staging, commit and hydration seams; `src/infra/adapters/pi-archive-adapter.ts` owns a working `InMemoryArchiveStore`, `TAIKNR_SIDE_STORE_TYPE` and three translation functions that throw (`Eleanor` §1; D9). `src/app/extension/taiknr.ts` already builds the session's config holder, the gated `pi`, the store, `argsByCallId`, the pending array and `originalContentByEntryId`, and registers the seven events (`Eleanor` §1; D7). Six of the seven handlers register and return; `session_start` loads config and leaves its store parameter unused (`Eleanor` §1).

The config holder those handlers read is already settled code, and its states are what every inertness claim below rests on. `SessionConfig` (`src/config/session-config.ts`) starts as `{ status: "unresolved" }`, takes `{ status: "ready", config }` or `{ status: "rejected", error }` at `session_start`, flips `config.enabled` in memory through `setEnabled(boolean)` only from `ready`, and defines `session.isActive()` as `state.status === "ready" && state.config.enabled`. `src/app/extension/taiknr.ts` registers `session_start` on the raw `pi` — so a later session start re-reads the config files and recovers from `rejected` or `enabled: false` — and registers the six other lifecycle events through `createGatedPi(pi, session)` (`src/app/extension/handler-gate.ts`), whose `on` wrapper checks `session.isActive()` at event dispatch time and returns `undefined` without calling the handler while inactive. What those states must make taiknr do is in `openspec/specs/configuration/spec.md` and is not restated here.

What shapes the approach is Pi 1.5.2's mechanics, measured rather than assumed:

- A run aborted with `Escape` never reaches `agent_before_settle`, so staging and settlement cannot be the same event (Trap 3; `Chidi` §2). A `context_edit` targeting a tool result that is no longer on the active branch throws, and one throwing draft discards the whole boundary, so the branch has to be consulted before anything is committed (Trap 3).
- `context_edit` replaces the target's entire content array and has no per-block form, so preserved image blocks must be carried by taiknr itself (`Chidi` §3; Trap 7).
- Pi's retry recovery omits a failed attempt's tool results with `context_edit(replacement: null)`, and a later stub edit for the same target resurrects an unpaired tool result (Trap 4). A `context_edit` entry carries no author (`Chidi` §3; M5), so the guard must be author-independent.
- `getBranch()` is the raw root-to-leaf path, keeps entries from before the latest compaction, and is what the branch hydration reads; `buildContextEntries()` is the compaction-bounded view (orientation §4 Q2; `Chidi` §5).
- Tool-result entry ids are normally eight hex characters but fall back to a 36-character UUID, and `toolResultEntryIds` is `flatMap`-filtered, so position is not a reliable pairing key (Trap 6; `Chidi` §1; S1).
- `JSON.stringify(undefined)` is `undefined`, and `JSON.stringify` leaves U+2028, U+2029 and U+0085 unescaped, so both the argument summary and the preview need one shared single-line transform (Trap 8; M9).
- Boundary drafts are committed after every handler returns, with no post-commit callback and no transaction, so in-memory success is not persistence (`Chidi` §2; M4).

What binds the design beyond the platform: Joel's Q1 → (a) (stage whatever the turn persisted, carry it to the next settled run) and Q2 → (a) (hydrate the whole branch), both ruled and not reopened; inertness enforced once at the composition root with one `session.isActive()` guard in the only ungated handler (D3–D5, Trap 2); `src/domain/` and `src/use-cases/` free of `@earendil-works/pi-*` (D6, ADR 0001); the seven registrations and the registrar, adapter and port signatures fixed against `HEAD` (D7); the tooling and lockfile untouched (D8); classifier scoring, the `/taiknr` command, caps and pruning out of scope (D10). `Modified Capabilities` is `None`, because every decision below lands inside those contracts (M7).

The council's findings and their dispositions are in `council.md`; this document records only the design that follows from M1–M11.

## Goals / Non-Goals

**Goals:**

- Stage every persisted, text-carrying tool result at or above the session's threshold at its own turn boundary, whatever that turn's outcome.
- Render a single-line stub that never splits a surrogate pair and never carries a line separator, and replace the tool result's content with it while keeping its non-text blocks.
- Commit a settled run's eligible items as one `taiknr-side-store` batch plus one replacement per item, in an order that cannot leave a stub without its raw record, and never commit an item the active branch no longer holds or one already carried by a `context_edit`.
- Rebuild the in-memory archive from the whole active branch on `session_start` (while active), `session_tree` and `session_compact`, skipping foreign and malformed entries without failing the event.
- Keep taiknr fully inert while off or rejected, prove it through the composition-root gate, and leave archive state observable without printing anything.
- Prove the runtime-only paths — abort, `/tree`, competing boundary drafts, compaction — against a real `AgentSession` with no model call.

**Non-Goals:**

- Classifier scoring, `<recalled_context>` injection, any adapter the recall card owns, and the `context` handler's body (D10; orientation §2).
- The `/taiknr` command and any status readout; `SessionConfig` and `setEnabled` stay untouched (D10; orientation §2).
- Archive caps, pruning and any ceiling on what hydration keeps (D10; Joel's Q2 → (a)).
- Any change to `package.json`, `package-lock.json`, `biome.json`, `tsconfig.json`, `vitest.config.ts`, `.gitignore`, the manifest metadata, `jev-context-poc.ts`, `test-jev-poc.mjs` or `~/.pi/agent/` (D8; orientation §2).
- Compatibility reading of PoC-era `jev-side-store` entries or `tc_N` ids (M2).
- Anything that rewrites a tool result before the run settles, which would hide raw output from the model mid-loop (Q1 → (d)).
- Any Markdown outside this change directory before the implementation is approved (S6; M11).

## Decisions

**Decision 1 — Stage at the turn boundary; settle at the run boundary.** `turn_end` stages whatever the turn persisted, for `completed`, `aborted` and `error` alike, keyed by the persisted tool result's own id (S1; Joel's Q1 → (a)). `agent_before_settle` consumes the pending list. *Alternatives weighed:* stage only when `outcome === "completed"` — leaves the aborted turn's own tool results raw for the rest of the session; drop items whose run never settled — leaves every result of an interrupted `bash` or build loop raw too; stub at `turn_end` — hides raw output from a loop still working and invalidates the run's prefix cache (Q1 → (b)–(d); `Chidi` §3).

**Decision 2 — Pair a tool result with its entry id by `toolCallId`, through `contextEntries`.** `toToolOutputCandidates` matches `event.context.contextEntries` for a projected entry whose `sourceEntry` is a `toolResult` message with the same `toolCallId` as the result, taking the last match, and falls back to `event.toolResultEntryIds[i]` only when `contextEntries` is absent and the two lengths agree (M7 step 2). Inside `toToolOutputCandidates(event, argsByCallId)` the unhappy paths are silent: a `toolResult` whose last-match lookup and length-checked fallback both fail to produce a non-empty `entryId` is skipped without failing the turn, and a call that was never seen at the tool-call boundary yields `argsSummary` `argsByCallId.get(tr.toolCallId) ?? ""` (S1; the stub spec's empty-argument-summary scenario). *Alternatives weighed:* blind positional indexing — silently mispairs when an id fails to resolve (Trap 6); object identity — undocumented and not a contract (`Chidi` §1; `ProjectedSessionEntry.sourceEntry` is public, M7's evidence).

**Decision 3 — Eligibility has one home, the use case.** `toToolOutputCandidates` stays pure translation: it collects `{ type: "text" }` blocks, sets `rawText` to their `"\n"` join when at least one block's text is non-empty, and `""` otherwise; `stageToolOutputs` stages only a candidate whose `rawText.length > 0 && shouldArchive(rawText.length, minCharsToArchive)`; `shouldArchive` and its `>=` test are untouched (M8). *Alternatives weighed:* the guard in the adapter (`CR-5`) or in both places (`R-5`) — either duplicates the rule and leaves future `cli/` and `mcp/` callers able to bypass it (D6; ADR 0001).

**Decision 4 — The stub renders a verbatim record; only rendered fields are normalized.** The stub is one line, `[archived <id>] <toolName>(<argsSummary>) status=<ok|error> (<n> chars, <m> lines) preview: <preview>` — the format `specs/archive-stubbing/spec.md` "The stub is one line naming the output and previewing it" owns, scenarios included, so none of them is repeated here. `ArchivedToolOutput.rawText` is `candidate.rawText` unchanged and `<n>` is its length. `<m>` counts a split on `/\r\n|\r|\n|\u2028|\u2029|\u0085/`, and `<preview>` joins that split's first three elements with `" | "`, cuts at 180 UTF-16 code units — at `max - 1` when the unit at the boundary is a high surrogate paired with the one at `max` — then applies `.toWellFormed()`. One exported helper in the same domain file, `summarizeSingleLine(text: string, maxUnits: number): string`, replaces `/\r\n|\r|\n|\u2028|\u2029|\u0085/g` with `" "`, cuts at `maxUnits` UTF-16 code units or at `maxUnits - 1` when the cut would split a surrogate pair, then applies `.toWellFormed()`; `buildStub` calls it with `120` on `candidate.argsSummary` and on `candidate.toolName`, and `tool-call.ts` calls it with `120` on `(JSON.stringify(event.input) ?? "")`, serialized inside a `try/catch` that substitutes `""` for any serialization throw — a `BigInt`, a circular reference, a throwing `toJSON` — so the helper is only ever handed a string, and `undefined` reaches it as `""` too (M9). *Alternatives weighed:* normalizing `rawText` itself — destroys the archive's content and the counts the stub reports; plain `String.prototype.slice` — splits surrogate pairs in text that is then permanent on the branch (M9's measurement: `("a".repeat(179) + "🚀").slice(0, 180).isWellFormed()` is `false`).

**Decision 5 — `argsByCallId` is a documented shortcut, not a managed cache.** `tool_call` returns early when `event.parentToolCallId !== undefined`, records the top-level call's summary of `event.input` — `""` when `JSON.stringify` throws or returns `undefined`, never a throw of its own (Decision 4) — and leaves the entry for the session's lifetime behind a one-line `shortcut:` comment (~120 characters plus a call id per top-level call, fresh per session closure) (M6 step 1). *Alternatives weighed:* clearing keys at `turn_end` — `turn-end.ts` holds `argsByCallId` as a `ReadonlyMap` and `agent-before-settle.ts` does not receive it, so clearing costs an `extension-packaging` delta while still leaking calls that never reach `turn_end` (M6's evidence); accepting the leak silently — the `shortcut:` comment is the recorded limit.

**Decision 6 — Original content is recorded only for what was staged.** `turn-end.ts` writes `originalContentByEntryId.set(item.id, content)` for each candidate `stageToolOutputs` actually staged, taking `content` from the last `ToolResultMessage` in `event.toolResults` whose `toolCallId` equals the candidate's, mirroring Decision 2's last-match rule — `ToolOutputCandidate` already carries both ids, so no re-resolution and no new adapter export (M6 step 2; M7 step 3). *Alternatives weighed:* recording every result — retains multi-MB base64 images for outputs that were never stubbed; rebuilding the content map at settle — needs a branch lookup that the settle event's own projection cannot do without a second pairing rule (M7 step 3; `CR-8`).

**Decision 7 — One settlement pass, drafts before mutation.** `agent_before_settle` runs M4's steps in one order, with every read and every draft finished before any state changes:

1. Read `ctx.sessionManager.getBranch()` and `event.entries`; build the active-branch `toolResult` id `Set` and the existing-`context_edit` `targetId` `Set` (Decision 8); partition `pendingOutputs` non-mutatingly into `committable` and `dropped`.
2. When `committable.length === 0`, remove the `dropped` items from `pendingOutputs` in place, delete their `originalContentByEntryId` keys, and return `undefined`.
3. Call `const drafts = toSettlementDrafts(committable, originalContentByEntryId)` — `[sideStoreDraft, ...contextEditDrafts]` — before mutating `pendingOutputs`, `originalContentByEntryId` or the store, so a throw leaves all three untouched.
4. Remove the `dropped` items from `pendingOutputs` in place and delete their `originalContentByEntryId` keys, then call `commitArchivedBatch(pendingOutputs, store)`, which drains the remaining `committable` items into the store, and delete the committed keys from `originalContentByEntryId`.
5. Return `{ entries: [...event.entries, ...drafts] }`.

Each `ContextEditEntryDraft` is `{ type: "context_edit", targetId: item.id, replacement: { content: [{ type: "text", text: item.stub }, ...nonTextBlocks] } }`, where `nonTextBlocks` is every block in `originalToolResultsByEntryId.get(item.id) ?? []` whose `type !== "text"`, in its original relative order; every original `type === "text"` block is dropped whatever its position, and a missing map entry yields `[stubTextBlock]` rather than throwing. Pi commits after all handlers return, with no post-commit callback, so the store is an optimistic cache over the branch (M4). *Alternatives weighed:* `CR-1`'s retention loop — keeps items pending until a `context_edit` appears on the branch, which re-stubs a pre-edit tool result after a `/tree` jump and holds images indefinitely for a finished session (M4's evidence); returning taiknr's drafts in place of `event.entries` — discards another extension's proposals (Trap 5).

**Decision 8 — Eligibility is two checkable conditions, author-independent.** A pending item commits iff `ctx.sessionManager.getBranch()` holds a `message` entry with `entry.id === id` and `entry.message.role === "toolResult"`, **and** neither that branch nor `event.entries` holds any `context_edit` with `targetId === id`, null replacement or not. The filter never reads `event.context.contextEntries`, whose compaction bound would drop carried-forward pre-compaction items. Both conditions are computed once per pass from two `Set<string>`s (~10 lines, in the handler, M7 step 4), and the drops are silent (M5). What the second condition sees depends on registration order, because Pi dispatches a boundary's handlers one at a time in load order — `ExtensionRunner.emitBoundary` (`runner.js:773-797`) calls each registered handler in turn, so `event.entries` holds only what the handlers *before* taiknr returned. A `context_edit` from an earlier-registered handler is therefore visible in `event.entries`, and the item is dropped with neither a stub nor a `taiknr-side-store` record written for that target. Handlers registered *after* taiknr run only once taiknr has returned, so taiknr cannot see their drafts: if a later handler appends `[...event.entries, itsEdit(targetId)]`, that edit still wins in model context under `buildSessionProjection`'s latest-edit-wins rule (`session-manager.js:264`), while taiknr's `taiknr-side-store` entry and `InMemoryArchiveStore` keep the unedited raw item; and if a later handler replaces `event.entries` without spreading, taiknr's drafts are dropped, which Decision 7's optimistic-cache rule already covers. *Alternatives weighed:* `replacement === null` only (`CS-3`'s original ask) — overwrites an earlier extension's redaction; reading `contextEntries` (`C-1`, `R-4`) — contradicts Joel's Q2 → (a); consulting the projection's latest edit — the same fact twice, and `ContextEditEntry` carries no author to filter on (`Chidi` §3).

**Decision 9 — The persisted payload is a bare array of complete domain items.** A `taiknr-side-store` entry's `data` is the batch: a non-empty `ArchivedToolOutput[]`, each item the whole object (`id`, `toolName`, `argsSummary`, `isError`, `stub`, `rawText`) (M1; M3). A well-formed item, defined once here and consumed by the write side and by the read guard, is a plain object — `typeof x === "object" && x !== null && !Array.isArray(x)` — with `id` a non-empty string, `toolName`, `argsSummary`, `stub` and `rawText` strings, `isError` a boolean, and any other property tolerated. On hydration, `readArchiveBatchesFromBranch` skips an entry whose `customType` is not `TAIKNR_SIDE_STORE_TYPE`, whose `data` is not a non-empty array, or any of whose elements fails the guard — whole entry, never per item — and folds the survivors in `getBranch()` order so `replaceAll`'s `Map.set` makes the last well-formed entry win a repeated id. A future incompatible shape gets a new `customType` (M1). *Alternatives weighed:* a `{ v: 1, items }` envelope (`R-3`) — `Array.isArray(data)` already identifies v1 and a bumped `customType` serves a break, so the envelope fails the deletion test; metadata-only items that re-join `rawText` from `toolResult` entries — duplicates the join rule across write and read and lets a changed `buildStub` diverge from the stored stub (M3).

**Decision 10 — Hydration is one path, `replaceAll`, on three events.** `session_start` hydrates from `getBranch()` only after the config state is assigned and only when `session.isActive()`; `session_tree` and `session_compact` hydrate through the gated `pi`, so the composition-root gate is the whole inertness mechanism for them (S4; D3–D5; Trap 2; `configuration` "The enabled switch turns taiknr fully off"). The mid-session flow follows from the states summarized in Context: `setEnabled(true)` from `ready` makes `isActive()` true again, so the next `session_tree` or `session_compact` reaches the gate open, while a later session start re-reads the config files and so also recovers from `rejected` or `enabled: false`. Reading the whole branch is what keeps pre-compaction outputs archived (Joel's Q2 → (a); `Chidi` §5), and whole replacement is what makes navigation drop the branch the user left. *Alternatives weighed:* `buildContextEntries()` — prunes the archive at `/compact` and contradicts Joel's ruling; hydrating only on start — leaves `/tree` and `/resume` stale, which is the PoC's bug (`Eleanor` §3); a per-handler `enabled` check — D4 forbids it.

**Decision 11 — No output, four named observation surfaces, per-handler error behaviour.** Archive state is observed through the `InMemoryArchiveStore`, the persisted `taiknr-side-store` and `context_edit` entries in the session JSONL, `SessionConfig.state`, and Pi's extension error channel; a silent drop is inferred from the absence of a `context_edit` for that id and the presence of a `taiknr-side-store` entry that omits it. There is no `console.*` and no logger (M11; `configuration-loader` ruling 14). Per handler, each one finishes its reads and its built values before it mutates anything: `turn_end` computes `candidates` and `staged` before it pushes to `pendingOutputs` or writes `originalContentByEntryId`; `agent_before_settle` builds its drafts before it mutates state (Decision 7); `session_start`, `session_tree` and `session_compact` finish `readArchiveBatchesFromBranch(ctx.sessionManager.getBranch())` before `hydrateArchiveStore` calls `store.replaceAll`, with `session_start` reading only after config assignment and only while active. Any unexpected throw in that shape reaches Pi's extension error channel without partial mutation (M11), because `ExtensionRunner.emitBoundary` (`runner.js:773-797`) and `emit` catch a handler's throw and report it there.

`tool_call` is the exception, and it is total rather than reported. `ExtensionRunner.emitToolCall` (`runner.js:965-979`) has no `try/catch`, `_beforeToolCall` (`agent-session.js:386-401`) rethrows, and `prepareToolCall` (`agent-loop.js:487-544`) turns a throw into `createErrorToolResult`, so a throwing `tool_call` handler blocks the user's tool call instead of reaching the extension error channel. `event.input` is mutable by earlier `tool_call` handlers (`types.d.ts:1005`), so the handler must never throw on any input: Decision 4's `try/catch` around `JSON.stringify` is what makes it total, and `undefined`, `BigInt` and circular inputs all record `""`. *Alternatives weighed:* a debug log — corrupts the TUI and JSON-mode streams and Pi ships no extension logger (M11).

**Decision 12 — Two test levels, and the shared fixture lands first.** `fake-pi.ts`'s `createContextStub` gains `branch` and `session-start.test.ts` passes a real store before any handler body lands, because eight existing session-start cases resolve `enabled: true` and would otherwise fail with a `TypeError` (Trap 1). Layer tests use `SessionManager.inMemory` and per-handler fixtures; one session-level test drives real `createAgentSession` with `SessionManager.inMemory` and a faux provider imported from `@earendil-works/pi-ai` in `tests/` only, behind a one-line `shortcut:` comment noting it is hoisted through `@earendil-works/pi-coding-agent` in the committed lockfile (`package-lock.json:667`) (M10), and that test isolates `PI_CODING_AGENT_DIR` and `cwd` per test the way `session-start.test.ts` does, since `taiknr(pi)` owns its `session` privately and no case may reach `setEnabled` from outside. `archive-session.test.ts` calls `await session.bindExtensions({ onError })` to run `session_start` and capture `ExtensionRunner` errors, and asserts observable `SessionManager` entries and the projected context end-to-end, while the three hydration handler tests — `session-start.test.ts`, `session-tree.test.ts` and `session-compact.test.ts` — assert `InMemoryArchiveStore` contents directly, with no prototype spies on `InMemoryArchiveStore`. *Alternatives weighed:* fixtures only — cannot reach Pi's abort-skips-settle and wholesale boundary-rejection paths (`CR-4`); the real session alone — slow and redundant for layer rules (M10).

## Risks / Trade-offs

- **An archived output's raw text exists twice in the session JSONL** — once in the raw `toolResult` entry, once in the side-store batch — so the archive roughly doubles the bytes of every stubbed output (M3). → Accepted and stated as an input for the archive-scaling card; nothing strips it here, because a stripped item would need a second text-join rule on the read path (`M3`'s evidence).
- **The archive and the recall payload grow with the branch** — a long session that archives many outputs without compacting keeps every item, and the next card's classifier sees all of them (Joel's Q2 → (a)). → Accepted; the ceiling is the archive-caps card's job (D10), and hydration applies none.
- **A boundary Pi discards leaves the store ahead of the branch** — one throwing draft from any extension makes Pi reject the whole boundary after `commitArchivedBatch` already wrote the store (Trap 3; `Chidi` §2). → The store is documented as an optimistic cache reconciled by `replaceAll` at the next `session_start`, `session_tree` or `session_compact`, and side-store-first draft order means a partial persist leaves no stub without its record (M4). Rollback of a stale item is the next hydration, not a compensating write.
- **An aborted run plus a `/tree` jump would crash the next settlement** — `appendContextEdit` on an off-branch id throws `Entry <id> is not on the active branch`, which discards every draft in the boundary (Trap 3's measurement). → Decision 8's filter runs and prunes before `toSettlementDrafts`, so no draft is ever proposed for an id the branch lost.
- **A recovery-omitted tool result could be resurrected as an unpaired result** — Pi omits a failed attempt with `context_edit(replacement: null)`, and a later stub edit for the same target makes it latest-edit-wins again (Trap 4). → Decision 8 disqualifies the item on *any* targeting edit on the branch, so the omission stands.
- **A stray `context_edit` from another extension could be overwritten by a stub** — a redaction or summary edit already on the branch, or one proposed at the same boundary, would lose to taiknr's later write (C-1; `CR-2`). → Same condition, and `[...event.entries, …]` keeps that extension's proposal in the boundary (Trap 5). A same-boundary edit's fate turns on registration order, as Decision 8 explains through `ExtensionRunner.emitBoundary`'s sequential dispatch: an earlier handler's edit is already in `event.entries` and drops the item, while a later handler's edit is invisible to taiknr, wins in model context, and leaves the unedited raw item in the store and in the `taiknr-side-store` record.
- **A mis-paired entry id would stub the wrong tool result** — `toolResultEntryIds` is `flatMap`-filtered, so a positional read can attach a stub to the neighbouring result (Trap 6). → Decision 2 pairs by `toolCallId` and allows position only as a length-checked fallback.
- **A surrogate split or a stray separator inside a permanently settled stub** — `JSON.stringify` leaves U+2028, U+2029 and U+0085 unescaped, and a naive 180-unit cut splits `("a".repeat(179) + "🚀")` (M9's measurement in Node 26.8.1). → Decision 4's shared helper and surrogate-safe cut, tested. The premise that a hosted provider rejects a lone surrogate was never verified (`CR-3`, abandoned rather than ruled), so the mitigation is adopted as cheap insurance.
- **`argsByCallId` grows for the session's lifetime** — roughly 150 KB across a 1,000-call session, never released (M6). → Accepted as a `shortcut:` with its limit written down, because releasing it legally would need a locked signature changed; per-session closure bounds it to one session.
- **A threshold below ~400 characters makes a stub longer than the text it replaces** — stubbing then grows context instead of shrinking it (CR-13). → Recorded for the docs pass; no code, because the configuration spec's valid range is the user's choice and `configuration` is not modified here.
- **The off → `/tree` → on sequence leaves a store the branch does not match** — the gate stops the tree handler while off, so a stale store survives until the next hydrated event (CR-12). → Handed to the Status and recall cards and the docs pass; the natural self-heal is any later `session_tree` or `session_compact` (orientation §2).
- **Inertness can regress silently** — a new handler wired to raw `pi` rather than the gate, or hydration added before `session.isActive()`, would stage or hydrate while taiknr is off (Trap 2). → Pinned by the named in-memory `setEnabled` toggle cases in `tests/infra/pi-event-handlers/turn-end.test.ts`, `.../agent-before-settle.test.ts`, `.../session-tree.test.ts` and `.../session-compact.test.ts`, and by the project-file `enabled: false` end-to-end coverage in `tests/app/extension/archive-session.test.ts`, alongside `tests/app/extension/handler-gate.test.ts` and `configuration`'s two archive-side scenarios (D5; `R-12`).
- **A malformed session file could break a session start** — a foreign or corrupt custom entry read from disk would throw inside `session_start`, before any other event runs, and the session would come up without an archive at best and with a failed extension at worst (O3). → Decision 9's guard skips the entry whole, and both deltas' scenarios pin that the session starts.

## Migration Plan

- **No data migration.** Nothing persisted changes shape for anyone: `taiknr-side-store` entries are written only by this build, `context_edit` entries are Pi's own type, and the guard reads a bare array — the first version of a format it defines (M1). Sessions written by the proof of concept carry `jev-side-store` entries and `tc_N` stub ids; they are ignored, with no legacy reader and no compatibility shim (M2).
- **Rollback is a revert, and it does not unstub.** Reverting the commit removes staging and settlement. Entries already written stay on their branches: `taiknr-side-store` is a custom entry Pi never sends to the model (`Chidi` §4), and an already-settled `context_edit` stub stays stubbed on its branch, which is ADR 0002's stated permanence (`Eleanor` §5). A revert therefore does not put already-stubbed output back into the model's context; the original is still reachable only by navigating to a branch that precedes the edit (`Chidi` §3). The in-memory store is not persisted state, so it needs no cleanup.
- **Verified floor.** This design was verified against `@earendil-works/pi-coding-agent` 1.5.2 only, and the package declares the host as `"*"` in `peerDependencies` (`extension-packaging` "Host-provided Pi packages are peer dependencies"), so nothing in the package stops an older host from loading it. The surfaces relied on — `agent_before_settle`, `context_edit` and `custom` boundary drafts, `getBranch()` and `session_tree`/`session_compact` — are the ones 1.5.2 provides (`Chidi` §1–§5); an older host is untested and out of this change's scope (R-8).
- **Post-merge hand-offs, in the docs pass only** (M11; S6; Joel's standing ruling that documentation never blocks a feature):
  - `AGENTS.md` line 3 and `ARCHITECTURE.md`'s introduction and §3 still describe every handler beyond configuration as a stub; they are wrong the moment this merges and are corrected in the docs pass.
  - Stubbing shrinks the model's context; it is not secret deletion or redaction. Raw tool results remain in the session JSONL, the UI and exports, and the side-store record holds their text (C-3).
  - Carry-forward lives only in the current extension runtime: it does not survive `/reload`, a new session or a session replacement, so items staged in a run that never settled are lost at that point (C-6).
  - The off → `/tree` → on handoff above belongs in the Status and recall cards' documentation as a known gap (CR-12).
  - A `minCharsToArchive` below about 400 can make a stub longer than the text it replaces; say so where the field is documented (CR-13).
  - The archive-scaling card receives two inputs: the duplicated raw text per item (M3) and branch-proportional growth with no ceiling (Joel's Q2 → (a)).
- **Nothing else runs after merge.** No migration script, no config change, no fixture seeding, and no test that touches `~/.pi/agent/` (`extension-packaging` "Load verification uses a throwaway agent directory").

## Open Questions

Both are deferrable: neither changes a spec requirement, the approach above, or the task breakdown.

- **What does a `context_edit` do to a provider's prompt cache?** Pi documents cache effects for system-prompt and tool changes and for an unchanged `context` list, but not for a mid-history `context_edit`; whether a hosted provider sees a byte-identical prefix up to the edited entry is an inference from Pi's implementation, not a promise (`Chidi` §3). The design does not depend on the answer: staging and settlement stay split so a run's own prefix is untouched until it settles, which is the point of the two-phase design (Q1 → (d); `council-catalyst`). Measuring it costs model calls and belongs to whoever takes the cost question up.
- **How does a terminal render a stubbed tool result that still carries an image block?** The projection layer was checked and confirmed to carry the stub text plus the original image (`Chidi` §3; Trap 7), but no live TUI was inspected, and orientation §5 records that gap. It is a visual question with no contract behind it, so it does not gate this change.
