# Council Synthesis

Seven lens reports, Michael's eighteen rulings on what they surfaced, and the artifacts they were run against. Each claim below names the lens and finding that made it and the ruling that decided it.

## Question and Scope

**The design question.** The archive half of taiknr is built and green: a large tool output leaves the model's context as a one-line stub and its raw text stays on the branch as a `taiknr-side-store` record. The recall half is still stubs — `formatRecalledContext` and `recallRelevantContext` throw, both `pi-context-adapter` exports throw, `PiJevScorerAdapter.score` throws, the registration is `_pi.on("context", () => {})`, and the notifier the composition root passes has an empty `notifyOnce` (Eleanor's report, §1; T7). `design.md` has to place working recall on those seams: which lifecycle event carries it, what the classifier sends and what selection does with its answers, what is appended where, how far one recall may grow, when recall yields, how a failure is reported once, and how all of it is proved without a live call.

**Constraints (binding).**

- **Joel's rulings** in `owner-rulings.md`: Q1(a) recall moves to the newest user message on a steer; Q2(b) and (c) a fixed timeout with no retries, held in a config field; Q3(b) highest-scoring first, stopping before pi's compaction threshold; Q4(a) one `ctx.ui.notify` per session; Q4's sub-question (a) a mistyped classifier model fails open; Q5(a) a live script checks the box, not Joel's manual test; Q6(a) one classifier call per new user message, with the spend invisible until the Status card. The standing rulings also bind: no fallback to defaults, distinct behaviour while `enabled` is false, the provider stays configurable-but-not-abstracted, and documentation never blocks a feature.
- **Michael's orientation decisions D1–D15** (`michael-orientation.md` §1): the card's decisions were proposals until Joel ruled; pi's context-usage undercount is assessed after this change (D2); the archive half and the Status card are out of scope (D5, D14); the seven-event list, the registrar, adapter and port contracts are frozen against `HEAD` apart from enumerated differences (D8, D15); `src/domain/`, `src/use-cases/` and `src/config/` import nothing from pi (D9); no `console.*` and no logger (D11); "once per session" means once per factory call (D13).
- **The settled observations S1–S11** (`michael-orientation.md` §5): recall registers on `context_with_system`; one call per key with one `bool` question per item; the model resolved through the catalog at event time; failure fails open; inertness lives in the composition-root gate; the cache key is the latest `role: "user"` message's timestamp plus its text; the layering of ADR 0001.
- **Traps the design must not walk into:** T1's prefix-cache cost under `context`; T2's live classifier call from the existing suite; T3's 300 s undici stall; T6's archive growth under an unchanged key; T8's resurrection of a redaction or another branch's output; T9's persisted compaction after overflow; T11's missing or trailing user message; T13's data flow and trust change; T14's invisibility; T15's `on`-only factory.

## Lens Findings & Trade-offs

Grouped by the question they bear on, not by lens. Finding ids keep their lens prefix: ZO is zoom-out, C critic, CR comprehension, F structural, R readiness, CB codebase.

**Where recall runs, and what it may change.** No lens asked to reopen S1, and the catalyst lens found no false compromise in the proposal's separation of persistent archiving from request-only recall. T1's measurement is why: under `context` the appended block rebuilds the head and drops the mid-conversation system message on models that accept them; under `context_with_system` the layout is `[system, user, assistant, system, …, user]` with the head unchanged (orientation T1). The one claim S1 does not support is C5's: because every `context` handler runs before every `context_with_system` handler, a request-time redactor never sees recalled text.

**The port, the failure notice and the notifier.** Four lenses converged on one shape and disagreed on its inverse. R1 and C2 found that the frozen port `RelevanceScore[] | undefined` carries neither the reason text nor the difference between a failure and a cancel, and that `createPiJevScorerAdapter` has no notifier to write the message itself. CB-2 read the same hole the other way: `undefined` for failure, `[]` for cancel. C7 added that a missing answer must never become probability 0, since `decisionThreshold: 0` is valid. Separately, R2, CB-1 and F7 found that the proposal's composition-root wiring for `createOncePerSessionNotifier` cannot be built at all — `ExtensionAPI` yields no `ExtensionContext`, and `taiknr.test.ts` allows only `on` at factory time — and CB-6 found that the notifier sets `warned` before it calls `notify`, so a stale-ctx throw consumes the session's only notice.

**The size bound.** C3, F1, R3 and CB-3 each found the same hole from a different side: the requirement mandates a bound but no artifact named where the window, the reserve or the current size come from, and the use case's input cannot receive any of them. R3 added that `ctx.model?.contextWindow` may be undefined and that `getContextUsage()` is `tokens: null` right after a compaction. F1 and C3 both attacked the absolute clause — "no request this change builds triggers the host's overflow recovery" — as stronger than a chars/4 estimate can deliver. CB-3's owner question named the remaining case: what recall does when the size cannot be known. ZO-1 concluded the packaging freeze had to be relaxed to carry the budget.

**The cache across a turn's requests.** C4 found that re-applying the bound on every request can shrink the recalled set mid-turn, changing the block's bytes and costing a rewrite of everything after it, while applying it once lets steps 2..n pass the threshold. R4 weighed the same two and noted a third cost either way. F4 found a contradiction between the spec's "reuse that scoring while the archive is unchanged" and proposal O2: the frozen `RecallCache {lastPromptKey, lastRecalledIds}` has no field to record that the archive changed. ZO-2 found the mirror-image problem for eligibility: a check made only per scored key lets a cache hit restore an item another extension redacted mid-turn.

**Eligibility and the scored set.** F3 found two requirements in the same delta disagreeing on whether ineligible items are scored, and tied it to Q6's cost framing: cost grows with the branch only if ineligible items are filtered before scoring, and D14's stale store makes the store larger than the branch. CR-C2 found the proposal's stub requirement stricter than the spec's "latest edit, if any". CB-7 supplied the two details that make the check buildable: `ContextEditEntry` carries no author, so authorship must be read from content, and taiknr's replacement is `[stub text block, ...non-text blocks]`, so only the first block may be compared. F2 found no artifact had verified that a handler can read the branch and its `context_edits` at request time.

**Claims the mechanism does not support.** C5's redactor bypass and C9's "never the archived payload": `buildStub` carries a 120-unit args summary and a 180-unit preview of the raw text, so the stubs are the payload's excerpt, not its absence (ruling 11, on `buildStub` and the measurement in ruling 9).

**Contracts and the freeze.** ZO-1 asked for one more packaging exception; CB-3 answered that the use case's input is not among the frozen shapes; R2 and CB-1 proposed workarounds for the frozen `notifier` member, one of which leaves a dead member. F6 found the place the scorer adapter is built unnamed, which its signature already forces: per event, inside the handler.

**The test side.** R8 and CB-5 counted four existing files that fail once the field and the event move land, none of them in the proposal's Impact list. CB-4 found the proposal's "keeps its pure test" false: `tests/domain/` holds one file, and no test anywhere mentions `selectRecalledIds`. R7 asked how a scripted classifier can prove the timeout at all, since a fake that honours `timeoutMs` proves only the fake. R9 found the credential guard described but unspecified, and CB-9 found the two harnesses — `createContextStub` without `ui.notify` or `modelRegistry`, and a session harness that writes no agent config and clears no credentials. R10 and CR-C3 found the live script unproved: no observation, no pass criteria, no failing run, and no way to load a TypeScript extension with `.js` specifiers under plain node.

**Compatibility.** R5 traced the rollback hazard: a user who sets `classifierTimeoutMs` and reverts gets an unknown-field rejection and an inert taiknr. R6 warned that a host older than `context_with_system` would recall nothing silently.

**The minors.** C6, F8 and R11 on the default timeout's derivation; C8 on its upper bound; CR-C1 on a timestamp collision; CB-8 on the cache's inability to distinguish "not scored" from "failed"; F5 on the no-live-call rule restated across two capabilities; CR-C5 and R12 on "tail" and the trailing user-role message.

**Reuse the council found, not new mechanism.** The classifier comes from pi's own `classify` with its native `timeoutMs` and `maxRetries`; the window from `getContextUsage()?.contextWindow`; the reserve from pi's own resolution chain over `pi.getSettings().compaction`; the size from pi's exported `estimateTokens`; the tests from pi-ai's real System One transport under a stubbed `fetch`; the live script's observation from `before_provider_request`. The repository supplies the recall use case, the domain formatter, the adapters, `RecallCache`, the `InMemoryArchiveStore` read path and the composition-root gate. No new dependency, no second tokenizer, no parallel subsystem.

## Synthesis & Recommendation

**Proceed to design.** Nothing in the council blocks: the layering holds, no data migration is needed, and the platform facts the two hardest requirements rest on were measured in this pass rather than assumed. The direction the rulings fix is the proposal's, narrowed where its claims outran its mechanism and made buildable where its wiring was impossible:

- Recall stays on `context_with_system`, appending one trailing text block to the latest `role: "user"` message and leaving every system message alone.
- The scorer adapter passes pi its own `timeoutMs` and `maxRetries: 0`; the port stays as it is; a failure crosses it as a rejection whose message is the finished notice, and only a cancel comes back as `undefined`.
- The budget is computed per request in the pi-aware handler from pi's own primitives, enters the use case as one host-neutral character allowance, and is re-applied to cached ids on every request; eligibility is likewise per request, filtered before scoring.
- The notifier is built inside the handler and the frozen `notifier` member is dropped rather than left unused.
- Both unsupported claims are calibrated to what the mechanism delivers, and the disclosure boundary is stated as the stub's three fields.

Each of those is Michael's ruling, not this document's judgment; the mechanisms and their evidence are in the next section but one.

What remains for `design.md` is what no ruling had to settle because it changes no requirement: O4's question wording and block format (including a raw text that carries the block's own delimiter), O6's treatment of a missing or trailing user message, the file and registrar names O8 leaves open, the default timeout's literal value, the migration plan's rollback order, and the placement of every new helper. The design also carries the two settled findings below, which must not be reopened unless their preconditions change.

### Amendments the rulings require

The proposal and the three deltas are left exactly as they stand in this pass. These are the edits the next pass applies, each with the ruling that requires it. A delta requirement that no entry names stays as written.

1. **`specs/extension-packaging/spec.md`** — requirement "Handler signatures and the import boundary are preserved". The delta carries only "The extension entry loads without error" today, so this requirement must be added as a MODIFIED copy whose "Signatures unchanged" scenario names one more enumerated difference: `registerContextHandler`'s dependency object drops `notifier`, and its `config`, `store` and `recallCache` members are unchanged. Nothing else moves — `createPiJevScorerAdapter` keeps its signature, `extractLatestUserPrompt` and `appendRecalledContextToMessages` keep theirs, `createOncePerSessionNotifier` keeps its signature, `RecallCache` keeps its shape and the port contracts stay. If the design renames `context.ts` or `registerContextHandler` (O8), that difference joins the same list. **Ruling 12**, made on **ruling 3**.
2. **`specs/tail-recall/spec.md`** — requirement "One call asks one bool question per archived item". "for every item in the archive" becomes "per eligible archived item", with eligibility defined by entry 3. **Ruling 9**.
3. **`specs/tail-recall/spec.md`** — requirement "Recall yields to edits taiknr did not write and to items off the branch". Delete "if any" and state both halves: (a) a tool-result entry with its id is on `getBranch()`; (b) the latest `context_edit` on the branch targeting that id has a non-null `replacement` whose **first content block** is text equal to `item.stub` — never the whole array, because a settlement writes `[stub, ...non-text blocks]`. Add two scenarios: an item with no edit (ineligible, because its raw text was never replaced), and an item that carried an image (eligible, because only the first block is compared). Add a third: a foreign edit landing under one cache key mid-turn (nothing recalled, no second classifier call). **Ruling 10**, and **ruling 8** for the per-request, cache-hit-included check.
4. **`specs/tail-recall/spec.md`** — requirement "Recall is scored once per latest user prompt". "while the archive is unchanged" is defined as the store's `size()` equalling its size at scoring, held in the existing `lastPromptKey` string, with no shape change. Add a scenario: a size change under the same user message scores again. **Ruling 6**.
5. **`specs/tail-recall/spec.md`** — requirement "Recall stops before the host's compaction threshold". Replace the guarantee with what the mechanism delivers — recall keeps the request at or under the compaction threshold by pi's own estimate — and delete "so no request this change builds triggers the host's overflow recovery", recording the residual risk against D2 instead. State that the window, the reserve and the current size are read per request. **Ruling 4**.
6. **`specs/tail-recall/spec.md`** — requirement "A failure fails open, with one notice in the session". Add that an answer set is accepted only when the stop reason is `stop` and every id asked about carries a bool answer with a finite probability in [0, 1]; every other answer set is an error answer. **Ruling 1**.
7. **`specs/configuration/spec.md`** — requirement "The classifier call's timeout is a field with a default that can be overridden". The field's range becomes an integer from 1 to 2147483647, and the rejection scenario gains `2147483648`. **Ruling 2**.
8. **`specs/tail-recall/spec.md`** — requirement "Recall is tested without a classifier call and verified by a live script run by hand". "clear every provider credential" becomes the concrete guard: one shared helper that stubs `fetch` with a recording stub, registers a provider under a distinct id that maps its classifier API to pi-ai's own System One `classify`, writes the agent config naming that provider and model, and clears `OPENROUTER_API_KEY` and `TYPESAFE_API_KEY`. The live-script half gains its observation (`before_provider_request` payloads recorded by a probe extension loaded after taiknr), its two pass conditions, the failing run that shows it catches a mistake, and the implementing coder as its runner. **Ruling 14** and **ruling 13**.
9. **`proposal.md`, "What Changes"** — the bullet "Recall stops before the host's compaction threshold" takes ruling 4's calibrated claim; the bullet "Recall yields…" takes ruling 10's no-edit case and first-block comparison; the bullet "One classifier call per key…" replaces "never the archived payload" with the stub's three fields (tool name, 120-unit args summary, 180-unit preview of the raw text, never the full raw text); the bullet "A failure fails open…" narrows "another extension's redaction is never undone" to persisted `context_edit` redactions and says request-time transforms do not cover recall. **Rulings 4, 10, 11**.
10. **`proposal.md`, Impact** — drop the composition-root notifier wiring for `src/infra/pi-event-handlers/context.ts` and `src/app/extension/taiknr.ts`; the notifier is built in the handler and the dependency object loses `notifier`. Add "keeps its pure test" correction for `src/domain/recall.ts`: `tests/domain/recall.test.ts` is a Create, and `selectRecalledIds`'s body does not change. Add the Modify entries the Impact list omits: `tests/app/extension/taiknr.test.ts`, `tests/app/extension/handler-gate.test.ts`, `tests/config/session-config.test.ts`, `tests/config/taiknr-config.test.ts`, `tests/app/extension/archive-session.test.ts` and `tests/support/fake-pi.ts`. Add the two limitations ruling 11 sends to the docs pass under the docs bullet. **Rulings 3, 11, 14, 18**.
11. **`proposal.md`, Open Questions** — O1, O2, O3 and O5 are closed by rulings 3, 6, 1 and 8/10; mark them settled and leave O4, O6, O7 and O8 to the design. **Rulings 1, 3, 6, 8, 10**.

Its two assumptions — that the owner's accepted costs are binding rather than compromises to reopen, and that the size bound deliberately rests on the host's estimate — are accepted as constraints above.

### Assumptions and what became of them

Every unverified assumption that mattered was measured in this pass. Structural's "an extension can read the branch and a request's size" became ruling 8's probe and ruling 4's measurements. Readiness's `pi.getSettings()` visibility, the version that introduced `context_with_system`, and the timeout's abort behaviour became rulings 4, 16 and 2. Critic's Node-timer question became ruling 2's overflow measurement; its Jev-latency question stays unmeasured and is recorded as a limit in the design. Comprehension's timestamp assumption turned out not to matter (ruling 7). What remains unchecked is listed per lens, and the ones the design must carry are: Jev's latency and recall quality beyond 30 items, the serialized provider-prefix bytes, OAuth-shaped auth latency, and RPC/print rendering of `notify`.

## Michael's Rulings

All eighteen are `settled`; none is `joel`. Each entry gives the dispute, the ruling, and what decided it.

**Ruling 1 — how a failure and a cancel cross the frozen port, and who writes the notice.** R1 and C2's mapping, with no port change: `score` resolves `RelevanceScore[]` only when the stop reason is `stop` and every id asked about carries a bool answer with a finite probability in [0, 1]; resolves `undefined` only when `ctx.signal` aborted; rejects in every other case — no catalog model, stop reason `error` (the timeout included), or an invalid answer set — with an Error whose message is the finished notice text. The adapter writes that text because only it holds the provider, the model, the config and pi's `errorMessage`, and the config field it names comes from a rule over facts the adapter holds, never from matching pi's wording. The use case wraps only the `score` call: on a rejection it calls `notifier.notifyOnce(error.message)`, records the key with no ids and returns `[]`; on `undefined` it returns `[]` with no notice and no key; on success it applies the threshold, ranks, fits and records. CB-2's inverse mapping is rejected because it throws away the reason text. *Decided by:* the frozen port in extension-packaging "Signatures unchanged", the tail-recall scenarios "The notice says what to fix", "A cancel is not reported" and "One attempt", Joel's "Orientation Q4 sub-question" (a), and ruling 2's measurement. *Evidence:* `ports.ts`'s two members, `createPiJevScorerAdapter` receiving no notifier, and a session-level probe on the real System One transport that returned `stop` with answers keyed by both an 8-hex and a 36-character id, turned a missing answer into stop reason `error`, and saw `findOfType` return undefined for a mistyped id.

**Ruling 2 — how the timeout is applied, told apart from a cancel, and proved.** `score` calls `ctx.modelRegistry.classify(model, context, { signal: ctx.signal, timeoutMs: config.classifierTimeoutMs, maxRetries: 0 })` and builds no timer or signal of its own. CB-2's premise holds only for an adapter-owned signal: with the native option pi reports a timeout as `error` with "Request timed out after N ms". `maxRetries: 0` is required, not cosmetic — without it the same 50 ms bound took 1,498 ms over three attempts. Auth resolution sits outside the bound, because `prepareRequest` calls `getAuth` before the timer starts; the design records that as a known limit for providers whose auth does network I/O and adds no outer guard, which would bring back the ambiguity. `classifierTimeoutMs` must be an integer from 1 to 2147483647, because a larger value makes Node warn and fire after 1 ms, turning the setting into "always fail". The suite proves the timeout by driving pi-ai's real path: a test-registered provider mapping its classifier API to pi-ai's System One `classify`, a global `fetch` that hangs until aborted, and a second case that aborts `ctx.signal` and sees no notice. *Decided by:* Joel's Q2 (b) and (c), pi-ai's source (`postClassifierRequest` throws its timeout error only when the timeout signal fired and the caller's did not; `maxRetries` defaults to 2; `system-one-shared.js` sets `stopReason` from the caller's signal), and the measurements: 51 ms for a 50 ms bound with one fetch, `"aborted"` in 22 ms for a caller abort, `"aborted"` in 52 ms for an adapter-owned signal, three attempts in 1,498 ms without `maxRetries`, and a TimeoutOverflowWarning plus a 1 ms firing for `AbortSignal.timeout(3e9)` under Node 26.8.1. Not checked: OAuth or credential-command auth latency.

**Ruling 3 — how the notifier gets a live ctx, and what happens to the frozen member.** Build the notifier in the handler and remove the frozen `notifier` member instead of leaving it unused. `registerContextHandler` calls `createOncePerSessionNotifier(() => current)` once at registration — once per factory call, which is once per session (D13) — and assigns `current = ctx` at the start of each `context_with_system` event, before any other work. The proposal's composition-root wiring cannot be built because `ExtensionAPI` yields no `ExtensionContext` and `taiknr.test.ts` allows only `on` at factory time; R2's `on` wrapper would put event-time ctx capture in the composition root through a second Proxy; CB-1's unused member is a compatibility shim with a dead placeholder behind it. `createOncePerSessionNotifier` keeps its signature and changes only its body: `warned` is set after `notify` returns, so a throw from a stale ctx cannot use up the notice — it lands in the runner's `context_with_system` catch and the request goes out unchanged. The same handler builds `createPiJevScorerAdapter(ctx, config)` per event from the holder's event-time config. *Decided by:* D13, D8 narrowed on the evidence, and `AGENTS.md`'s rule that a handler owns its event-time reads. *Evidence:* `types.d.ts` shows `ExtensionAPI` has no member returning a context, `taiknr.ts`'s placeholder, `pi-notifier-adapter.ts`'s `warned = true` before `getCtx().ui.notify`, `context.ts`'s dependency object, and `runner.js`'s catch-and-continue around a `context_with_system` throw.

**Ruling 4 — where the size bound's inputs come from, in what unit, and what recall does when one is missing.** Every input is read per request, in the pi-aware handler. **Window:** `ctx.getContextUsage()?.contextWindow`, pi's `_limitsModel()` — the routed model when there is one — with `tokens` unused; when it returns undefined, recall nothing and make no classifier call, which answers the codebase owner question, since Q3(b) already chose a recoverable missed recall over a persisted compaction. **Reserve:** `pi.getSettings().compaction` resolved as `getCompactionTokenSetting` does — `modelOverrides["provider/id"].reserveTokens`, then `reserveTokens`, then `DEFAULT_COMPACTION_SETTINGS.reserveTokens` — with a `shortcut:` comment citing `settings-manager.js` because pi exposes no resolved accessor; the bound applies whatever `compaction.enabled` says. **Current size:** the sum of pi's exported `estimateTokens` over the event's own messages, system messages included — never `getContextUsage().tokens`, which counted a request-only 40,000-character block through the provider's usage (11,399 against 1,386 measured), is null after a compaction, and cannot see this request's steer or other handlers' edits. **Unit:** 4 × (window − reserve − estimate) characters, matching pi's chars/4 rule; the use case fits whole items by the length of the domain's formatted block, so the domain holds no tokenizer and the formatter has one home. Those inputs, plus ruling 8's eligible ids, enter through `RecallRelevantContextInput`, which is not one of the frozen shapes. **Claim:** the spec, the proposal and the new ADR are to state that recall keeps the request at or under the threshold by pi's own estimate, and not that it never triggers overflow recovery; the residual risk is recorded against D2. No margin is added beyond `reserveTokens`, because Joel chose Q3(b) knowing the estimate undercounts and no source supplies a margin value. *Decided by:* Q3(b), D2, what extension-packaging "Signatures unchanged" actually freezes, and the measurements: step 1's usage equalled the event estimate at 1,383; step 2's usage read 11,399 against 1,386; in-memory settings returned a raw `compaction` with no defaults applied. *Evidence read:* `dist/index.d.ts` exporting `estimateTokens`, `shouldCompact` and `DEFAULT_COMPACTION_SETTINGS` from the package root; `agent-session.js`'s `_limitsModel`, threshold check and `getContextUsage`; `settings-manager.js`'s override-then-setting-then-default chain. Not checked: the routed (virtual) model path.

**Ruling 5 — how the cache and the size bound interact across one key's requests.** C4's rule. On a new key: score the eligible items, select by the threshold, rank by descending probability, keep the longest prefix whose formatted block fits this request's budget — stopping at the first item that does not fit, never skipping to a smaller one — and record the key and the kept ids. On a cache hit: take the recorded ids, keep only those still in the store and still eligible, and append that block only if it fits this request's budget whole. The block's bytes stay identical across the turn's requests and change only when the block is dropped or an item turns ineligible, each costing one cache rewrite from the user message onward, which the design states. R4's two options are rejected: step-1-only breaks Q3(b) on steps 2 to n, and a ranked list reshapes `RecallCache`, which D8 freezes through the registrar's dependency type, buying partial recall in a near-threshold edge case at the price of one prefix rewrite per dropped item. `lastRecalledIds` keeps meaning what its name says; a cached id that hydration removed is skipped, never dereferenced. *Decided by:* Q3(b), D8, and S1/T1's purpose of a stable cached prefix. *Evidence:* the `RecallCache` shape, the context registrar's dependency type, the living "the other members of both objects unchanged", and the orientation's P2 probe showing each request carries only its own recall block.

**Ruling 6 — the spec's "while the archive is unchanged" against the frozen cache shape.** Keep the clause and define it: "unchanged" means the store's `size()` equals its size at scoring, compared through the existing `lastPromptKey` string. No shape change and no delta. A size change under the same user message scores again, which covers both cases R4 and T6 describe, because items enter the store only at settlement or hydration. A same-size swap under the same key is accepted as a possible missed recall, never a wrong one, since ruling 8's per-request eligibility check drops ids from another branch. This closes proposal O2, and the spec scenario names the trigger. *Decided by:* the tail-recall delta's reuse clause, D8, and Q6(a). *Evidence:* the `RecallCache` shape and the wiring that writes the store only at settlement (`addBatch`) and hydration (`replaceAll`).

**Ruling 7 — comprehension's timestamp collision.** No change; the finding is contested. A collision needs the same text in the same millisecond and, with ruling 6, the same store size. The classifier's input is only the prompt text and the eligible stubs, so a fresh call would receive exactly what the cached scoring was computed from. Where recall goes does not depend on the key: each request appends to the latest `role: "user"` message by its index (`ExtractedUserPrompt.messageIndex`), so a colliding steer still carries the recall and Q1(a) holds. The only difference from a fresh call is the classifier's own nondeterminism. No collision test is needed, and the finding is recorded as settled: do not reopen it unless the key or the classifier state changes. *Decided by:* S8, the frozen `ExtractedUserPrompt`, S2, and Q1(a). *Evidence:* `pi-context-adapter.ts` places the block by index and re-derives the index every request; pi's steering timestamps were not measured, and the ruling does not depend on them.

**Ruling 8 — whether eligibility is checked per scored key or per request.** Per request, cache hits included. Before each append the handler reads `ctx.sessionManager.getBranch()` and derives the eligible id set by ruling 10's rule, through one helper beside `readArchiveBatchesFromBranch` in the archive adapter. The set goes inward as host-neutral data; the use case applies it to the scoring candidates and to the cached ids, with no second classifier call. No archive handler, store hook or branch revision is added. *Decided by:* S9 and ADR 0005, the tail-recall yield requirement, pi 0.87.0 committing boundaries at every `turn_end` so a foreign edit can land between two requests under one key, and the measurement: a probe handler's `getBranch()` on a second prompt carried entry types including `context_edit`, taiknr's edit whose `replacement.content[0].text` equals the side-store item's stub, and the item's id as a branch entry.

**Ruling 9 — whether ineligible items are scored.** Eligible items only, and not Joel's question. Eligibility is a filter applied before scoring, with one home, and applied again on every request; the requirement reads "one bool question per eligible archived item". Three reasons: Q6 accepted a cost growing with the branch, not the store; scoring a redacted item would send taiknr's stub — whose 180-unit preview is the text the redaction removed — to OpenRouter, undoing the redaction off the machine against ADR 0005 and S2/T13; and a question about an item that can never be recalled has nothing that uses its answer. *Decided by:* Q6(a) as about 160 tokens per item growing linearly with the branch, ADR 0005, and S2/T13. *Evidence:* `buildStub` carries the first three lines of raw text as a 180-unit preview, plus a 120-unit tool name and args summary.

**Ruling 10 — the eligibility rule's content.** The proposal's rule, with "if any" removed. An item is eligible only when a tool-result entry with its id is on `getBranch()`, **and** the latest `context_edit` on the branch targeting that id has a non-null `replacement` whose first content block is text equal to `item.stub`. Compare only that first block, never the whole array, because a settlement writes `[{type: "text", text: item.stub}, ...non-text blocks]`; authorship is read from content because `SessionEntryBase` carries no author. An item with no edit has nothing to recall: its tool result was never replaced, its raw text is already in context, and appending it would duplicate it — a case that arises only when a `/tree` leaf lands between a batch's side-store entry and its edits. The yield requirement gains two scenarios, an item with no edit and an item that carried an image. *Decided by:* ADR 0005, the archive write path putting the side-store entry and every `context_edit` in one boundary, and ruling 8's measurement.

**Ruling 11 — the two overclaiming claims.** Narrow both and keep S1, which no lens asked to reopen. The proposal, the spec and the new ADR say persisted `context_edit` redactions are never undone, that request-time transforms by other extensions — in `context` or in an earlier-loaded `context_with_system` handler — do not see recalled text, and that the classifier payload passes through no request-time transform at all. The disclosure sentence says what leaves the machine: the prompt's text and each eligible stub, being the tool name, a 120-unit args summary and a 180-unit preview of the raw text; the full raw text never leaves. Both limitations go to the docs pass, with README and ARCHITECTURE §7 saying plainly that prompts and stubs leave the machine by default and that request-time redactors do not cover recall. This calibrates claims and changes no mechanism; because the bypass is a user-facing consequence of S1, the conductor names it to Joel at the PL2 gate. *Decided by:* pi's runner order (every `context` handler, then every `context_with_system` handler), `buildStub`'s fields, and the feature-spec standard's rule that claims match the mechanism.

**Ruling 12 — whether the contract freeze must be relaxed.** One more enumerated difference, and only one: the packaging delta modifies "Handler signatures and the import boundary are preserved" so that "Signatures unchanged" lists a fourth difference — `registerContextHandler`'s dependency object drops `notifier` (ruling 3). Nothing else moves: the event name is already in the delta; `RecallRelevantContextInput` gains the budget and eligible ids with no delta because it is not frozen; `RecallCache` keeps its shape; the port contracts stay; `createPiJevScorerAdapter`, `extractLatestUserPrompt`, `appendRecalledContextToMessages` and `createOncePerSessionNotifier` keep their signatures, the adapter built per event inside the handler from the holder's event-time config, the notifier changing only its body. O8 stays the design's call, and a rename adds one more difference to the same list. *Decided by:* the living "Signatures unchanged" scenario, D8, and rulings 1 to 6. *Evidence:* the living spec's text, `context.ts`'s dependency type referencing `RecallCache`, the use case's input interface referenced by no handler signature, and the four adapter and port declarations.

**Ruling 13 — the live verification script.** Who runs it is settled by Q5(a), not a new question: the implementing coder runs it as part of the verification task, using the provider credentials already in Joel's environment the way Chidi took the measured round trip, and ticks the box only on a passing run. Its shape: a root-level `.mjs` outside the test include and the lint allowlist; loaded through pi's own loader, `DefaultResourceLoader({ additionalExtensionPaths: [repoRoot] })` under plain node, because importing `src/` directly fails on the `.js` specifiers; a throwaway `PI_CODING_AGENT_DIR` holding its own config, with the user's credentials passed explicitly and nothing written under `~/.pi/agent`; the real classifier from that config with a real main model; and an inline probe extension loaded after taiknr recording `before_provider_request` payloads, so it observes at the request. It exits non-zero unless both hold: a prompt asking for a unique marker in one archived output is sent with exactly one recall block carrying that marker at the tail of the latest user message, with earlier messages and every system message byte-identical to a request without recall; and an unrelated prompt is sent with no block. The design records a failing run that proves the script catches a mistake, and the script removes its throwaway directories on every exit. *Decided by:* Q5(a), the development-checks spec's exclusion of a root-level file, and the measurements: a root-level `.mjs` loaded `src/app/extension/taiknr.ts` through the manifest and ran a prompt with no extension errors, while `import("./src/app/extension/taiknr.ts")` failed with ERR_MODULE_NOT_FOUND. No live call was run in this pass.

**Ruling 14 — keeping the default suite off the live classifier.** One shared helper under `tests/support/` owns the guard, used by every session-level recall test and by `archive-session.test.ts`: it stubs `fetch` with a recording stub that answers scripted System One JSON or hangs until aborted, which is the guard because pi-ai resolves `globalThis.fetch` at call time; it registers a provider under a distinct id such as `taiknr-test` — never a second `openrouter` — through an inline extension's `pi.registerProvider`, mapping its classifier API to pi-ai's own System One `classify` with a literal key; it writes `<agentDirectory>/pi-taiknr.json` naming that provider and model; and it clears `OPENROUTER_API_KEY` and `TYPESAFE_API_KEY` with `vi.stubEnv`, restoring with `vi.unstubAllEnvs` and `vi.unstubAllGlobals`. One test shows the guard catching a mistake: under the default openrouter config with a dummy key, the stub records the `.../systemone` URL. The two existing prompts after settlement get a scripted "no" and keep their assertions unchanged. That file and `tests/support/fake-pi.ts`, which gains a recording `ui.notify`, become Modify entries. *Decided by:* T2/S7, the development-checks requirement that no live model or classifier call is made, and the measurements: a stubbed `fetch` under the test-registered provider received the System One request and parsed scripted JSON into answers; under the default openrouter route with a dummy key, `classify` posted to `https://openrouter.ai/api/v1/systemone` while `getProviderAuthStatus` reported `configured: false`. *Evidence read:* `classifier-shared.js` resolving `options.fetch ?? globalThis.fetch`.

**Ruling 15 — whether recall keeps calling the classifier after the first failure.** (a) Keep calling, and it is not Joel's question. Q6 accepted one classifier call per new user message; Q2's no-retry applies within one call and the spec's "One attempt" per key; Q4 gives one notice per session. Stopping for the session would add a circuit breaker no ruling asks for and would turn a network blip into recall staying off until reload. The design states the cost: a classifier that is down adds up to `classifierTimeoutMs` to each new user message, silently after the first notice, while a missing model or an unconfigured provider fails at once with no added latency. Joel can revisit once the Status card can show failures. *Decided by:* Q6(a), Q2(b), Q4(a) and the "One attempt" scenario. *Evidence:* with no key, `classify` returned "Provider is not configured: openrouter" at once with no network call; a mistyped model made `findOfType` return undefined; a hung call cost exactly the bound, 51 ms for 50 ms.

**Ruling 16 — version skew with the host.** Contested: no new skew. pi's changelog adds `context_with_system`, the actionable `turn_end`/`agent_before_settle` boundaries and `ContextEditEntry` in one release, 0.87.0; the already-shipped archive half depends on the last two, so any host that can stub can recall. The packaging spec already pins load verification to 1.5.2 and keeps the peer range `*`. The design records 0.87.0 as the floor both halves share and adds no detection. Recorded as settled. *Decided by:* pi 1.5.2's `CHANGELOG.md` lines 790, 798 and 800 under "## [0.87.0]", and the packaging spec.

There is no data migration, because recall writes nothing and no stored format changes, so a session this build recalled, resumed by an older build, carries no trace of recall. *Decided by:* Joel's standing "Q1 … B" ruling, the configuration spec's rejection of an unknown key, and the tail-recall requirement "Recall writes nothing". *Evidence:* `taiknr-config.ts` raising `TaiknrConfigError(filePath, field, "unknown field")` for a field outside `FIELD_RULES`.
